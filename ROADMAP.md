# hammertools — roadmap e status

Toolkit de "addons" pro Hammer++ (Garry's Mod) sem tocar no binário: marcadores `ht_*` no editor → CLI Python reescreve o VMF. Um pacote, um CLI, um FGD.

Atualizado em 2026-09-26. Sprints 1 a 4 concluídos e validados no jogo.

## Instalação e atualização (Windows)

- **Usuário**: baixe `install.ps1` do último release (github.com/EchoRPgm/hammertools/releases) e rode `powershell -ExecutionPolicy Bypass -File install.ps1` com o Hammer++ fechado. Instala o uv (sem admin), o Python 3.12 gerenciado e o `ht` (com numpy/scipy) e roda `ht setup`. `-Token` é opcional (só limite da API).
- **`ht setup`**: acha o GMod pela Steam (registro + `libraryfolders.vdf`, qualquer disco), grava o FGD em cp1252, aponta o `BSP` do gameconfig do Hammer++ pro `ht-vbsp.exe`, põe o FGD nos `GameDataN`, cria `ht-lint.cmd` e as sequências "ht lint"/"ht final". Idempotente; com o Hammer++ aberto ele desfaz o gameconfig ao fechar.
- **Atualização**: no início de cada compile (`ht-vbsp` consulta sempre, timeout 3 s; com versão nova instala e roda o compile num processo filho com o código novo, que o Hammer++ espera; offline/erro compila com a versão atual) e no fim de cada comando `ht` (1 consulta por dia). Instala o wheel novo no mesmo ambiente (`uv pip install --python <python do ht>`; no Windows renomeia os `ht*.exe` em uso antes) e roda `ht setup --refresh`. `ht update` força; `ht update --auto off` só avisa; `HT_NO_UPDATE=1` desliga. Checkout do git nunca se atualiza.
- **Repo público desde 2026-10-03** (histórico reescrito com `git filter-repo --replace-text` pra tirar a chave do Windows-MCP do `vm-share/setup.ps1`, que agora recebe `-AuthKey`). Token é opcional. O download do asset segue um 302 pra URL assinada que recusa `Authorization`: com token, urllib e PowerShell 5.1 repassariam o header, então os dois baixam em duas etapas (Location sem seguir, depois sem token).
- **Publicar**: `tools/release.sh X.Y.Z` (árvore limpa + testes, grava `__version__`, commit `chore(release)`, tag `vX.Y.Z`, push). `.github/workflows/release.yml` confere tag = versão, roda os testes, gera wheel/sdist e cria o release com notas automáticas + `install.ps1`.

## Como usar (Hammer++)

1. Coloque os marcadores (ferramenta de entidade, `Shift+E`, digite `ht_` no combo Objects). Pares: `ht_x` com os parâmetros + `ht_x_end` só de posição, mesmo targetname. Tubo usa `ht_pipe_node` com `order`; escada em curva usa `_ctrl`.
2. Salve. Pra ver o resultado no editor: Run Map → Expert → **"ht preview"** → Go → File → Reload. Esconda/mostre pela checkbox do visgroup `ht_preview`. **"ht preview clear"** remove.
3. Compile normal (F9 → OK). O `ht-vbsp` limpa o preview do fonte, gera `mapsrc\build\<mapa>.vmf` e o BSP vai pra `garrysmod\maps`. Recarregue o mapa no Hammer++ depois (ele avisa que o arquivo mudou).
4. No jogo, `map <nome>` no console pra recarregar (ou `gmod.exe -hijack +map <nome>`).

## Arquitetura

- **Marcadores**: `ht_x` (início, todos os parâmetros) + auxiliares `ht_x_end` / `ht_x_node` / `ht_x_ctrl` (só posição e, no node, `order`), ligados pelo mesmo `targetname`. O FGD não tem campos condicionais, por isso classes separadas. `core/vmf.base_class` / `role_of` agrupam; keyvalue `role` antigo ainda é aceito.
- **Geradores**: `generators/<nome>.py` com `@register("ht_x")` e `generate(vmf, group) -> Result(solids, ents, warnings)`. Constroem em coordenadas locais (+X = do início pro fim) e posicionam com `brush.place` / `place3d`; entidades com `brush.to_world`.
- **Build**: `ht build fonte.vmf [-o saída] [--game dir]`: descarta `ht_preview`, roda geradores, adiciona em `ht_generated/<targetname>`, esconde marcadores em `ht_markers`, grava arquivo novo. Nunca sobrescreve o fonte; recusa `_built.vmf` como entrada.
- **Preview**: `ht preview fonte.vmf`: mesma geração, dentro do fonte em `ht_preview` (regenerado a cada rodada, marcadores visíveis). `--clear` remove.
- **ht-vbsp**: `hammertools.cli:vbsp_main`. Recebe os args do Hammer (`-game <dir> <path\file>`), limpa o preview do fonte (desligue com `HT_KEEP_PREVIEW=1`), faz o build em `build\`, chama o vbsp real (achado via `-game`, ou `HT_VBSP`) e copia `.bsp/.prt/.lin/.log` de volta pro lado do fonte.
- **Modelos**: `core/models.py` lê bbox de `.mdl` via `srctools.game.Game(gamedir).get_filesystem()`. Precisa da pasta do jogo (`--game`, `HT_GAME`, ou o `-game` do ht-vbsp).
- **func_detail**: `add_generated`/`add_preview` embrulham os solids do grupo num `func_detail` (visibilidade não é cortada, vvis rápido). `Result.detail` é o padrão do gerador (duto oco = False), `detail` no marcador sobrescreve. Nos testes, `conftest.all_solids`/`gen_solids` enxergam mundo + func_detail.
- **Convenções**: unidades Hammer; vértices de geometria curva arredondados pro `grid` do marcador (padrão 1); saída sempre em arquivo novo; cada gerador tem entrada no FGD, módulo e teste.

## Notas técnicas (o que custou a descobrir)

- **srctools 2.7.0**: `Solid.export(include_groups=not _is_worldspawn)` está invertido e some com visgroups de brushes de mundo. `core/vmf.py` faz monkeypatch em `Solid.export`.
- **Normais**: `Side.normal()` aponta PRA DENTRO do solid. `PrismFace` do `make_prism`: west = face -X, east = +X, north = -Y, south = +Y. `Side.from_plane` recebe normal pra dentro e inventa pontos fora do grid; por isso geometria inclinada/curva usa `brush.from_points` com 3 pontos explícitos (winding igual ao `make_prism`: cross(p2-p1, p3-p1) pra dentro). Se `point_inside` do centro der False, o winding está invertido.
- **Eixos de textura**: `Side(planes=...)` do srctools sai com uaxis/vaxis padrão (`[0 1 0]`/`[0 0 -1]`), degenerado em faces com normal ±Y → o engine desenha a face VERMELHA. `brush.from_points` chama `reset_uv()` em cada face. Sintoma no jogo: face vermelha lisa (não é textura faltando, que seria xadrez rosa/preto).
- **Modelos com origem no centro**: `props_c17/door01_left` tem origem no meio da altura (z −54..54) e largura 48 (y −1..47 a partir da dobradiça); `ht_door` lê o bbox e sobe a origem (`model_z=auto`). `light_cagelight01_on` pende pra baixo da origem (z −11..2).
- **`ht lint`** (`hammertools/lint.py`, `core/geom.py`, `core/gma.py`): checagens `markers, outputs, textures, models, leak, nodraw, duplicates, overlaps, grid, tjunctions` (`--only`/`--skip`). Recursos do jogo pela classe `Resources` (injetável nos testes). Pasta do jogo: `--game`, `HT_GAME` ou a instalação padrão do GMod. Voxel automático ~320 células no eixo maior (mín. 8u); `--voxel` força. Na VM: sequência "ht lint" no Run Map Expert. Mapa real (rp_surdonoso, 9 mil brushes): ~7 s.
- **Nodraw à vista**: (1) ponto 1u à frente do centro da face fora de brush visível; (2) sonda de voxel só no trecho LIVRE até o primeiro brush que o raio acerta (antes atravessava o piso de baixo e achava a sala debaixo dele: laje sobre vão fechado de 81u no rp_surdonoso); (3) alguma entidade pontual fora de sólidos, a até 3000u, com linha de visada até a face (cordas, landmark, lógica, overlay, cubemap não contam; prop a <64u não conta, o modelo costuma tampar). O aviso diz quem enxerga. Vão fechado grande dentro do selo (debaixo do terreno) não conta mais. (4) Displacement bloqueia a visada pela SUPERFÍCIE (`geom.disp_triangles`, grade do SDK: linha y ao longo de p0→p1, coluna x ao longo de p0→p3, cross(p1−p0, p3−p0) contra a normal), nunca pelo brush-base, que pode ficar longe do terreno. (5) Prop tampa: ponto a 2, 8 ou 16u à frente da face dentro da caixa girada do modelo (piso do modelo de elevador 5u acima do brush nodraw) (view_bbmin/max do studiohdr em 128/140, hull em 104/116 se zerado) = escondida (batente nodraw atrás do modelo de janela). (6) Brush translúcido/água com face nodraw não acusa: não é sólido pro vbsp, a face só deixa ver através (vidro de janela com o lado de dentro nodraw). (7) Prop de cenário (caixa > 256u: árvore gigante, torre) não é testemunha. (8) Cobertura por amostras (centro + 1/3 e 2/3 até cada vértice), exposta = ≥25% descobertas: o centro sozinho falhava quando caía numa quina (rampa nodraw embaixo de degraus que só encostam nas quinas); a sonda/visada parte da primeira amostra exposta, que vira a posição do aviso. rp_surdonoso: 705 → 15. Limite: face que só o jogador andando vê, sem entidade por perto, passa batido.
- **Faces fantasma / textura vazada** (`hammertools/bspcheck.py`, checagem `phantom`, precisa do BSP compilado deste VMF: `--compiled` ou `<mapa>.bsp` mais novo que o VMF): face do mundo desenhada sem face visível de brush no lugar (fantasma) ou com textura que nenhum brush de mundo tem ali (vazada). **Causa** (código do vbsp, `src/utils/vbsp/portals.cpp`, `FindPortalSide`): faces do mundo nascem dos portais da árvore BSP e levam a textura da PRIMEIRA face coplanar da folha; brushes de mundo com texturas diferentes no mesmo plano, sem corte da árvore na divisa, fazem uma textura cobrir as outras e até um vão. Sensível à árvore inteira (tirar um piso do outro lado do mapa fazia sumir). rp_surdonoso: entrada da escada (3257 -10898 -316) virava parede de CONCRETEWALL001 atravessável, invisível no Hammer, desde o VMF original. **Hint não serve** (só muda onde a árvore corta: uma caixa resolveu o vão, outra piorou). **Conserto validado**: no plano do problema, fica no mundo o grupo de textura dominante e os outros acabamentos viram func_detail (faces próprias, sem FindPortalSide). O **ht-vbsp** faz sozinho após compilar (detecção 3 s), só no build/, até 2 rodadas, volta pro anterior se vazar/falhar, registra em `.tjfix.json` (`phantom.detail`); problemas < 256u² ficam só no lint. Faces de detail sobre o mundo não contam (o defeito só atinge o mundo). Mapa inteiro depois do conserto: 0 grandes, 1 lasca fantasma de 109u² e 1 vazamento de 24u².
- **Material de modelo em brush** (checagem dentro de `textures`): shader `VertexLitGeneric` e afins numa face de brush não recebe lightmap, a luz sai errada e muda com a distância (grama da calçada em 5337 -9769). `ht fix` cria cópia `LightmappedGeneric` com os mesmos parâmetros de textura em `materials/<mapa>_fix/...` (pasta de conteúdo do mapa) e troca só nas faces de brush, gravando `<mapa>_fix.vmf`.
- **Nodraw, testemunhas**: lista do que PODE ser testemunha (`VIEWERS`: spawn, info_node, props, luzes, npc, itens, sprites, soundscape) em vez de lista do que não pode; lógica (info_target, lua_run) ficava em qualquer canto e no gm_fork "via" faces escondidas. A sala da skybox 3D (espaço do sky_camera) não conta como área jogável.
- **Mapas de referência analisados** (2026-09-27): RP Rockford (`-notjunc`, 99,4% dos vértices, 80% detail, 56% dos vértices no grid 8), gm_fork (fonte público; compila com FixTjuncs a 55%; visibilidade por fade de props e func_lod, func_viscluster; vbsp modificado só por func_detail_blocker/opções), InfMap Vice City (mundo em modelos desenhados e colididos por Lua). Os tetos de vértices e índices de t-junction (65536) são do formato BSP v20 (índices de 16 bits), nenhum vbsp modificado muda.
- **Relatório HTML** (`hammertools/report.py`, `ht lint --html [arquivo]`, padrão `<mapa>.lint.html`): aba **Painel** (cartões por prioridade: leak > marcadores > I/O > texturas > modelos > t-junctions > prop_static dinâmico > nodraw > sobreposições > duplicados > grid; e pontos quentes em blocos de 1024u somando todas as checagens), Texturas (por material, filtro por pasta), Texturas por região (proximidade single-link, `--cluster-radius`), Modelos, T-junctions (densidade em blocos de 512u ponderada por vértice, top 300 faces com os pontos exatos), Leak (caminho), Geometria, Entidades. Todo local tem botão `setpos` (console, 64u acima) e `xyz` (Hammer++ Ctrl+Shift+G). **Áreas** (`--area-size`, padrão 1024u): blocos fixos de grade numerados pelo total de problemas (os mesmos do "Onde concentrar esforço"); toda localização leva `data-area`. Barra comum a todas as abas: filtro opcional por área (esconde linhas e localizações fora dela, aba mostra "N na área", tabela vazia vira aviso; botão "filtrar esta área" no painel) e "Agrupar por área" (reordena as linhas de cada tabela sob cabeçalhos de área, pela área que mais aparece na linha). Filtro e agrupamento ficam salvos no navegador. Agrupamento single-link encadeia o mapa inteiro quando é denso (t-junctions viravam uma região de 8000u): por isso densidade usa célula fixa.
- **T-junctions**: o vbsp (FixTjuncs) para com "Too many t-junctions" acima de 65536 índices primitivos. A estimativa do lint é teto (não desconta faces que o vbsp remove), então é só ranking/aviso. ATENÇÃO: o número que o vbsp imprime no erro ("65556 indices") é onde ele PAROU ao passar do limite, não o total do mapa; o total real é desconhecido (o original parou em 65556 e o `_opt` em 65550, sem dizer quanto falta). Não dá pra calibrar a estimativa por esse número. Experimentos na VM (2026-09-27): `_opt` (249 junções) ainda estoura; SEM nenhum func_detail compila com o FixTjuncs ligado (o excesso vem de detail e detail x mundo); func_detail → func_brush (4197 entidades) troca o problema por "Too many unique verts" (65536), inviável. rp_surdonoso: 93% dos vértices são inteiros em arestas alinhadas, vindos de vizinhos de TAMANHOS diferentes (parede tocando piso maior no meio da aresta), não de fatias iguais. **Como o vbsp trata** (mapa mínimo na VM, contando PRIMINDICES no BSP): faces do mundo e de entidades de brush (func_brush) são cortadas pela árvore BSP do próprio modelo e a t-junction some (0 índices, custa vértices); faces de func_detail NÃO são cortadas e viram primitiva triangulada (42 índices no teste). Quem gasta o teto é o detail (e o mundo que recebe vértice de detail). O BSP publicado do rp_surdonoso já saiu com `-notjunc` (0 prims) e usa 59.610 de 65.536 vértices. **Conserto automático no ht-vbsp**: ao estourar, ranqueia os func_detail por custo (`optimize.rank_detail_tjunctions`: índices das faces dele + 3 por vértice dele no meio de aresta alheia, via `sources` do lint) e converte os K piores em func_brush sólidos com `vrad_brush_cast_shadows 1`, um por bloco de 1024u (`optimize.detail_to_brush`; teto de ~1024 modelos), K = 100, 200, 400, 800, 1600, 3200, todos; não para no primeiro que compila: segue até índices <= 90% do teto (folga pra editar), com travas de vértices <= 97% e modelos <= 90% de 1024 (modelos previstos antes de compilar = 1 + entidades de brush exceto func_detail + func_brush novos; conferido no BSP depois); passou de trava ou outro teto = fica com a melhor tentativa que compilou (arquivos `_best` restaurados); outro teto ("Too many unique verts") ou fim do detail = volta o build original e usa `-notjunc`. Só no build/, o fonte fica com func_detail. rp_surdonoso: K=100 e 200 estouram, K=400 (82 func_brush) compila com FixTjuncs (64.023 índices reais, 60.658 vértices, 437 modelos), todos (263) estoura vértices. Medido (bloco de 1024u): K=800 → 53.559 índices (82%), 61.347 vértices (94%), 480 modelos; K=1600 (por contato) → 41.679 / 63.434 (97%) / 782.
